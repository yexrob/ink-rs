# resize 残影：清屏重放留给应用
- 日期：2026-10-20
- 状态：已实施
- 提交：（无）
- Brief：（无）

## 背景
M3 合入后，用户在 herdr 中试用 demo，附截图问：「resize 重绘是还没做到哪里是吗？」

Claude 在 tmux 中复现，抓字节流后定位两个原因，都实测确认：
- 折行行数估少了。tmux 折行时，行内含非 ASCII 字符的，每个宽字符按 3 列计，因为它把宽字符后的占位格也算 1 列；用 `\x1b[K` 擦掉的行尾也计入行宽。103 列缩到 61 列时，三条任务行各折成 2 行，ink-rs 估为 1 行，光标少上移 3 行。
- 旧帧顶部被挤进 scrollback。tmux 折行后光标所在屏幕行号不变，多出的行从屏幕顶部推进 scrollback。光标移动够不到 scrollback，不清 scrollback 就擦不掉。

Ink 按旧行数擦除，两类残影都有，留下的行更多。herdr 的终端内核是 ghostty-vt，折行规则与 tmux 不同；截图中 Static 行从行中间开始，Claude 的推测是残留行带软换行标记，未实测。

## 决策
- 按终端选择折行规则（A）不做，留给应用。用户：「A 我觉得可以留给应用去做。」
- 清屏、清 scrollback 再重放（B）不进库。用户先表示「B我觉得可以」，Claude 拟出 `Options::replay_on_resize` 方案后，用户问：「其实是不是B这种方案本质也不是在ink里面的 claude code单独在应用层面处理的？」Claude 确认 Ink 没有这种机制，建议 B 不进库。用户：「你修复一下demo就行了 我看看效果」，之后回复「好的 没问题了」。
- 库不改动。

## 备选与取舍
- A：检测 `$TMUX` 时按 tmux 规则估算。能修好第一个原因，修不了第二个；ghostty 的规则还要另测。
- B 进库（`Options::replay_on_resize`，默认关闭）：宽度变小，或高度变小且上一帧高度达到新行数时，输出 `CSI 2J`、`CSI 3J`、`CSI H`，重放 Static 与 `use_stdout` 历史，再画当前帧。代价：清掉程序启动前的终端历史，历史无上限地留在内存；库只能重放旧宽度的字节交给终端折行。
- B 在应用层：应用重新渲染条目，Static 内容按新宽度布局。Claude 认为优于库内重放。

## 方案
Claude 在 demo 中加约 12 行，不经 Codex：
- 用 `use_window_size` 发现宽度变小；
- 用 `use_stdout().write("\x1b[2J\x1b[3J\x1b[H")` 清屏、清 scrollback；
- 给 `Static` 换 key，使全部条目重新输出。

窗口变宽时不处理。只在 tmux 中验证：先用 `seq 60` 填满屏幕，103 列缩到 61 列，没有残影，scrollback 清空，Static 条目按 61 列重排。herdr 中的效果由用户查看。

## 结果
- 库没有改动。
- 清屏后屏幕第一行是空行，来自外部写入在数据不以换行结尾时补的 `\r\n`。Claude 请用户决定是否修，这次没改。之后 `f2e2514`（20:15）修了「以换行加转义序列结尾时多出一个空行」的情况，记录中未见它与本条空行的关联。
- Claude 建议在 design.md 记下 tmux 的宽字符折行限制。当前 design.md 中没有找到这条说明，记录中未见补记。
- 现行的 resize 规则见 [终端输出](../design.md#终端输出)。
