## 1. What to build

### 1.1 `ink_rs::Error`

A public enum in a new module `src/error.rs`, re-exported at the crate root:

```rust
pub enum Error {
    Io(std::io::Error),
    App(Box<dyn std::error::Error + Send + Sync>),
}
```

- `Io`: a terminal I/O error, the errors `wait_until_exit` returns today (including EPIPE).
- `App`: the error the app passed to `AppHandle::exit_with_error`.
- Implement `Debug`, `Display` and `std::error::Error`. `Display` and `source` forward to the inner error (the `#[error(transparent)]` pattern, written by hand; no new dependency), so `error.to_string()` gives the message, as Ink's `error.message` does.
- `From<std::io::Error>`.
- Rustdoc on the type and each variant.

### 1.2 `AppHandle` exit methods

```rust
pub fn exit(&self)
pub fn exit_with(&self, value: impl Any + Send)
pub fn exit_with_error(&self, error: impl Into<Box<dyn std::error::Error + Send + Sync>>)
```

Rules (design.md 退出):
- The result of `wait_until_exit` is `Ok(None)` for `exit()`, `Ok(Some(Box::new(value)))` for `exit_with(value)`, and `Err(Error::App(error))` for `exit_with_error(error)`. `Into<Box<dyn Error + Send + Sync>>` accepts `&str` and `String`, so `exit_with_error("Done")` works.
- The first request wins. A request after the queue closes (`UpdateQueue::close`, called by `Runtime::begin_unmount`) is ignored, as is any request after the first. This covers calls from effect cleanups during teardown and from other threads after unmount.
- The call records the request and wakes the driver, like `update`. It never unmounts inside the call.
- The queue lock must not be held across user code or the drop of a user value (see the comment in `UpdateQueue::drain`). An ignored request's value or error is dropped after the lock is released.
- The request lives in the queue state beside the callbacks. Keep it a `pub(crate)` detail.
- Update the rustdoc of `AppHandle` and `Scope::use_app`: they now exit the app too.

### 1.3 `App` honours the request

- At the end of every `App::render_if_due` step (after the passive effects), if the queue holds an exit request, the app unmounts with `App::unmount` and the step returns `None`. `App::unmount` already gives the teardown order of design.md 退出: commit pending work, write the pending frame, run the tree cleanups, restore the terminal. Raw mode comes later and will slot in first.
- Because App does this, the sync driver (`render`, `rerender`, `clear`, `wait_until_exit`) and `TestApp` share the behaviour. After it, the existing paths are no-ops (`App::rerender`, `App::clear` and `App::unmount` already check `runtime`).
- App keeps the exit result for the driver to take. Combine it in one place, in App, by the first failure:
  1. an exit error (`Err(Error::App)`);
  2. a terminal I/O error raised during the unmount (`take_error`);
  3. otherwise `Ok(value)` (`None` for `exit()`).

### 1.4 The sync driver

- `Instance::wait_until_exit(self) -> Result<Option<Box<dyn Any + Send>>, Error>`.
- `run_loop` gains a stop for the exit. Check it after `render_if_due` and its error check, and before `natural_end`. This matters: after the app unmounted itself, a handle the caller still holds keeps `natural_end` false, and the loop would block in `recv` for ever.
- An exit that happened before `wait_until_exit` (in the first step of `render`, in `rerender` or `clear`) makes `wait_until_exit` return the result at once.
- Results: a loop stopped by an I/O error returns `Err(Error::Io)`; a stop by exit returns App's combined result; the natural end returns `Ok(None)`, or `Err(Error::Io)` for an I/O error during the unmount, as today. Signals do not change.
- Rustdoc on `wait_until_exit`: the three results, and that a caller ends a blocked wait from outside by calling `exit()` on a handle taken with `Instance::handle` before waiting (design.md 退出; Ink tests call `unmount()` from outside).

### 1.5 `TestApp`

- `pub fn exit_result(&self) -> Option<&Result<Option<Box<dyn Any + Send>>, Error>>`: `None` while the app runs, then the result App combined. Rustdoc says exits come from `AppHandle` requests, which the next step honours.
- `testing::render` (`TestInstance`) has no App and does not change: a request there has no effect. Say so in the rustdoc of `Scope::use_app` or `testing::render`, whichever reads better.
