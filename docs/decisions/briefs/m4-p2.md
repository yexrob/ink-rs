## 1. What to build

### 1.1 Public API

- Add `Error::Panic(PanicError)`.
- `PanicError` holds:
  - `message: String`: the `&str` / `String` payload, otherwise `"Box<dyn Any>"`, as std's hook prints it;
  - `location: Option<PanicLocation>` with public `file`, `line` and `column` (1-based);
  - a captured backtrace, private;
  - `payload: Mutex<Box<dyn Any + Send>>`. The `Mutex` keeps `Error: Sync`.
- `PanicError` methods: `message()`, `location()`, `into_payload()`.
- `Display` prints the message, and `source()` is `None`.
- The `PanicError` docs say three things:
  - `std::panic::resume_unwind(e.into_payload())` after `wait_until_exit` gives the usual exit code 101;
  - nothing is caught under `panic = "abort"`;
  - a component's own `catch_unwind` suppresses std's message for the panics it catches.
- No new `Options` field and no user error boundary; Ink has neither.

### 1.2 Hook coordination (the blocking issue)

Today the driver hook restores the terminal before unwinding starts. That drops every later write, so the overview could never reach the screen. Std's hook also prints over the frame.

Add a core module, `src/runtime/panic.rs`:
- Its thread-locals: a capture depth set around the guarded regions, an "unwinding" flag, and the captured location and backtrace.
- `install()` runs under a `Once` and is called from `App::new`, so `testing::mount` installs it too.
- The hook rule:
  - if capturing (`!cfg!(panic = "abort")` and depth > 0) and the flag is not set: set the flag, record the location and `Backtrace::capture()`, and return without calling the previous hook;
  - otherwise, call the previous hook.
- A hook call that arrives while the flag is set is a panic in a `Drop` during unwinding, which std turns into an abort. It takes the uncaught path, so the terminal gets restored.
- Use `try_with` for the thread-locals.
- The driver hook in `process.rs` checks the same condition and skips the restore for a panic that will be caught. Either installation order must work.

### 1.3 Catching in the runtime

`Runtime` gains `catch: bool` and `panic: Option<PanicError>`.
- App sets `catch`. `begin_unmount` clears it. `render_to_string` and `testing::render` never set it.
- The guard is `catch_unwind(AssertUnwindSafe(..))` around three regions:
  - the whole `reconcile` call in `commit`;
  - the layout-effect group: cleanups, drain, `effects(true)`;
  - the passive group, and the drains in `after_write`.
- Leave these uncaught, for Ink parity: input and paste handlers, `AppHandle::update` closures, and Transform functions in layout and paint.
- The first caught panic is recorded; later ones are dropped.
- A panic while committing the overview itself propagates with `resume_unwind`, so a broken overview cannot loop.
- After a render or layout-effect panic, set `next` to an empty root and continue the commit's round loop. The mismatch path retires the user tree, and its cleanups run inside the guarded drains.
- After a passive panic, only record it. The next commit replaces the tree.
- Comment why `AssertUnwindSafe` is sound: after a caught panic, the runtime never observes the half-updated subtree again.

### 1.4 App

After `commit` and after `passive_effects`, when the runtime reports a panic:
- rerender the root with the overview element;
- request exit with `Err(Error::Panic)`;
- re-commit within the same step when the panic happened inside `commit`.

Exit precedence: a panic replaces a pending `Ok` exit but not an earlier `Err`. Implement this as a request on `UpdateQueue`, not as a special case in App.

The step then ends through the existing `has_exit` → `unmount` path: raw mode off, the overview painted, cleanups, restore, result. That is Ink's `handleExit` → `unmount` → `finishUnmount` order.
- A panic in the first render inside `render()` unmounts during the first step. `wait_until_exit` then returns the stored result.
- On the alternate screen, leaving the screen discards the overview, as Ink does.
- Non-interactive mode writes the overview as the final frame at unmount, as for any final frame.

### 1.5 The overview element

The builder lives in an app-level `src/error_overview.rs`. It produces a plain View/Text tree with no components, mirroring Ink's `ErrorOverview.tsx` layout and colors (research §1):
- padding 1;
- ` ERROR ` with a red background and white foreground, followed by ` {message}`;
- the location `{file}:{line}:{column}`, dim;
- the source excerpt, 3 lines around the error line:
  - read the file with `fs::read_to_string(file)` relative to the cwd, and skip the excerpt on any error;
  - split on `\r?\n` and convert only leading tabs, to 2 spaces each;
  - line numbers are dim, and the error line has a red background;
- the stack, when the backtrace was captured (see 2.3), one row per frame.

The path is `Location::file()`. Strip the cwd prefix from absolute paths.

Add `#[track_caller]` to the user-facing asserts, so locations point at the user's code: `State::get/set/update`, `OutputWriter::write`, and the `FocusManager` mutators that can panic.

## 2. Decisions

1. A panic replaces an earlier `Ok` exit in the same step, but not an earlier `Err` (design.md's first-failure rule).
2. No catching during teardown. Panics in the final cleanups take today's uncaught path.
3. Stack section:
   - Shown only when `Backtrace::capture()` captured frames (`RUST_BACKTRACE` or `RUST_LIB_BACKTRACE` set).
   - Parse the `Display` output best-effort:
     - drop the leading std, core, panic and ink-rs hook frames;
     - `N: symbol` followed by `at file:L:C` becomes `- symbol (file:L:C)`;
     - a frame without a location becomes a raw `- …` line.
   - No `backtrace` crate.
   - No "run with RUST_BACKTRACE=1" hint in the overview.
4. `testing::render` and `render_to_string` do not catch; a panic fails the Rust test with std's message.
5. Transform panics are not caught.
6. Alternate screen: the overview disappears with the screen (Ink parity). The caller still gets `Err(Panic)` with the message and location.
