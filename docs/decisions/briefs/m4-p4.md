## 1. Public API

```rust
// Feature "tokio", on by default.
impl Scope {
    /// Spawns `f()` with `tokio::task::spawn_local` after the commit, like `use_effect`.
    pub fn use_future<D: PartialEq + 'static, F: Future<Output = ()> + 'static>(
        &mut self,
        deps: D,
        f: impl FnOnce() -> F + 'static,
    );
}

// ink_rs::tokio, cfg(all(unix, feature = "tokio")).
pub mod tokio {
    pub fn render(element: impl Into<Element>, options: Options) -> Instance;
    pub struct Instance; // !Send, like the sync Instance
    impl Instance {
        pub fn rerender(&mut self, element: impl Into<Element>);
        pub fn clear(&mut self);
        pub fn handle(&self) -> AppHandle;
        pub fn unmount(self);
        pub async fn wait_until_exit(self) -> Result<Option<Box<dyn Any + Send>>, Error>;
    }
}
```

Semantics match the sync driver unless this brief says otherwise. Inside the crate, name the external crate `::tokio` to avoid the clash with the module.

Docs on `ink_rs::tokio`:
- `render` and `wait_until_exit` must run inside a `tokio::task::LocalSet` or a local runtime, because `use_future` calls `spawn_local`. Give a `no_run` example with `#[tokio::main(flavor = "local")]` (stable in tokio 1.54).
- Dropping the `wait_until_exit` future unmounts the app.
- A sync `ink_rs::render(..).wait_until_exit()` called on the same thread blocks every task on it.

Docs on `use_future`:
- The previous task is aborted when `deps` change and when the component unmounts.
- A running task keeps the app alive: `wait_until_exit` does not reach its natural end while one runs. A bare `spawn_local` holds nothing; capture `cx.use_app()` in it to get the same effect.
- A panic in the task is a component panic: the app shows the error overview and `wait_until_exit` returns `Err(Error::Panic)`.
- Panics outside a `LocalSet` or local runtime (from `spawn_local`). Tasks need a driver that yields to the runtime: `ink_rs::tokio`, or `testing::mount` inside a `LocalSet`.

## 3. Driver design

### 3.1 Message sink

`ProcessTerminal::new`, `ProcessTerminal::register`, `stdin::Target` and the registry `Entry` hold `mpsc::Sender<Message>` today. Replace it with one trait:

```rust
pub(super) trait Post: Send + Sync + 'static {
    fn post(&self, message: Message);
}
impl Post for std::sync::mpsc::Sender<Message> { /* ignore send errors */ }
#[cfg(feature = "tokio")]
impl Post for ::tokio::sync::mpsc::UnboundedSender<Message> { /* ignore send errors */ }
```

Store `Arc<dyn Post>`. `UnboundedSender::send` is synchronous and needs no runtime context, so the reader thread, the signal thread and `Wake::wake` (called under the queue lock) can post. `Wake` for the app queue posts `Message::Wake`; one impl over `Post` types or one per sender, your choice. `Message::Stop` keeps its `std::sync::mpsc::Sender<()>` ack.

### 3.2 Shared mount

Move the body of the sync `render` (environment lookup, `resolve_interactive`, color level, `register`, `App::new`, `set_wake`, the first `render_if_due`) into one function both drivers call with their sink and their clock reading. Put the fields both `Instance` types share (`app`, `registration`) in one struct with the shared methods (`rerender`, `clear`, `handle`, `Drop`), so neither `Instance` duplicates them. The sync and tokio `Instance` wrap it with their receiver.

### 3.3 Shared loop step

`run_loop` mixes the per-iteration work with the wait. Extract the iteration so the drivers differ only in how they wait and how they run a suspension callback. A shape that fits:

```rust
#[derive(Default)]
struct Looper { input_ended: bool, kept: VecDeque<Message> }

enum Next {
    /// Wait for one message until the deadline, then call `turn` with it.
    Wait(Option<Instant>),
    /// The terminal is handed over. Run the callback, then call `resume`.
    Suspend(Box<dyn FnOnce() + Send>),
    Stop(Stop),
}

impl Looper {
    fn turn(
        &mut self,
        app: &mut App,
        registration: &mut Registration,
        first: Option<Message>,
        poll: &mut dyn FnMut() -> Option<Message>,
        now: &dyn Fn() -> Instant,
    ) -> Next;
    /// After a suspension callback: rejoin the loop and resume (Reason::Api).
    fn resume(&mut self, app: &mut App, registration: &mut Registration);
}
```

`turn` holds everything `run_loop` does today: input coalescing with non-input messages as barriers, Stop / Continue / Resize / Signal / InputStarted / InputEnded, errors, `render_if_due`, exit, `begin_suspension` with `leave_loop` and the Stop-ack drain into `kept`, the natural-end check with its one extra poll. Keep the existing comments with the code they explain. Keep a sync `run_loop(app, receiver, registration) -> Stop` built on `Looper`, so `src/driver/tests.rs` changes only where signatures changed. Sync behavior must not change.

### 3.4 tokio loop

- Clock: every `now` for a tokio app comes from `::tokio::time::Instant::now().into_std()`: mount, `rerender`, `clear` and the loop. A paused tokio clock then drives the app.
- Wait: `Wait(Some(deadline))` → `::tokio::time::timeout_at(deadline.into(), receiver.recv()).await`, a timeout or a closed channel gives `None`; `Wait(None)` → `receiver.recv().await`.
- Suspend: `::tokio::task::spawn_blocking(callback).await`. Other tasks on the runtime keep running while the child owns the terminal; their `State` writes commit without painting, as in the sync driver. If the callback panicked, `std::panic::resume_unwind` its payload on the UI thread without calling `resume`, which matches the sync driver, where the panic unwinds out of the loop. Otherwise call `Looper::resume`.
- `wait_until_exit` mirrors the sync one: enter the loop, run, leave the loop, drain remaining messages (releasing Stop acks), unmount, take the error, drop the registration, map `Stop` to the result. On `Stop::Signal` await `std::future::pending::<()>()` instead of parking the thread: other apps on this thread must run their cleanups, and the last registration terminates the process.

### 3.5 Registration rules

`enter_loop` treats a same-thread in-loop entry as a suspended outer loop (nested sync waits). With tokio:
- several tokio apps on one thread run concurrently, not nested: a tokio app enters the loop without marking anyone;
- a sync wait on a thread that runs tokio apps blocks all of them: the sync `enter_loop` marks every same-thread in-loop entry as out of the loop (today it marks the first one found), and its `Drop` puts all of them back.

## 4. `use_future`

In `src/runtime/hooks.rs` (or a small module next to it), `#[cfg(feature = "tokio")]`. Build it on `use_effect`; take the liveness handle inside the effect, not on every render:

```rust
// sketch
self.use_effect(deps, move || {
    let alive = queue.handle(); // the app's UpdateQueue; an AppHandle
    AbortOnDrop(::tokio::task::spawn_local(Guarded::new(store_weak, async move {
        let _alive = alive;
        f().await;
    })))
});
```

- `AbortOnDrop` aborts the `JoinHandle` on drop (effect cleanup on deps change and unmount).
- Panics: a task polls on the UI thread outside every runtime guard, so today the driver's process panic hook would restore the terminal and tokio would swallow the panic, leaving a live app with a restored terminal. Poll the task's future inside the core capture (`runtime::panic::guard(true, ..)`), and on a panic hand the `PanicError` to the runtime so the next step reports it like an effect panic (`take_panic` → `report_panic`: overview, then `Err(Error::Panic)`), and wake the loop (`queue.notify()`). After a panic the task ends. A small `Future` wrapper does this; no new dependency. If the runtime is gone, drop the error. Choose where the runtime keeps the handed-over panic (for example a slot on `Store` that `take_panic` also checks) and explain the choice in the report.
